# Human in the Loop עם LangGraph

פרויקט הדגמה קטן: סוכן שכותב טיוטת תשובה ללקוח, **עוצר לפני השליחה**, ומחכה שאדם יחליט מה עושים איתה.

## איפה אנחנו

כבר ראינו איך שולחים פרומפט למודל ומקבלים תשובה. ראינו גם ש-LangChain נותנת לנו לחבר פרומפט, מודל ו-parser לשרשרת אחת.

מה שמוסיפים עכשיו הוא **שליטה בזרימה**: גרף של שלבים, עם מצב (state) שעובר ביניהם, ועם נקודה אחת שבה הגרף עוצר ומעביר את ההחלטה לבן אדם. זה Human in the Loop.

לא ניכנס כאן לכלים (tools), לסוכנים מרובים או לשמירת state במסד נתונים אמיתי. נגיע לזה בהמשך.

## למה זה מעניין אותנו

מודל שפה טועה. לפעמים בטון, לפעמים בעובדה, לפעמים בהבטחה ללקוח שאין לנו כיסוי עבורה.

כל עוד הוא רק מציע טקסט, טעות כזו זולה. ברגע שהוא **מבצע פעולה** (שולח מייל, מחזיר כסף, מוחק רשומה) הטעות כבר יצאה החוצה ואי אפשר להחזיר אותה.

Human in the Loop הוא הדרך לתת למודל לעשות את רוב העבודה, ולהשאיר לאדם את הרגע שבו מתחייבים. אפשר לחשוב על זה כמו code review: המפתחת כותבת, אבל שום דבר לא נכנס ל-main בלי שמישהו אישר.

## הזרימה

```
START
  │
  ▼
write_draft  ◄──────────┐   המודל כותב טיוטה
  │                     │
  ▼                     │ revise (עם הערות)
human_review  ──────────┘   ⏸ interrupt: הגרף עוצר ומחכה לאדם
  │        │
  │ approve│ cancel
  │ / edit │
  ▼        ▼
send_email END
  │
  ▼
 END
```

בנקודת העצירה לאדם יש ארבע אפשרויות:

| פעולה | מה קורה |
|---|---|
| `approve` | שולחים את הטיוטה כמו שהיא |
| `edit` | האדם כותב את הנוסח הסופי בעצמו, ושולחים אותו |
| `revise` | האדם כותב הערה, והטיוטה חוזרת למודל לתיקון |
| `cancel` | עוצרים בלי לשלוח |

## ארבעה מושגים שצריך להבין

### 1. State

ה-state הוא מילון (`TypedDict`) שכל ה-nodes בגרף רואים. כל node מקבל את ה-state הנוכחי ומחזיר **רק את מה שהשתנה**. LangGraph ממזגת את העדכון לתוך ה-state בעצמה.

```python
class EmailState(TypedDict):
    customer_message: str
    draft: str
    feedback: str
    status: str
```

### 2. `interrupt()`

זה הלב של הפרויקט. כשקוד בתוך node קורא ל-`interrupt(...)`, הגרף נעצר, שומר את המצב, ומחזיר את השליטה לקוד שהריץ אותו. הערך שמעבירים ל-`interrupt` (כאן: הטיוטה והשאלה) מגיע החוצה תחת המפתח `__interrupt__`.

```python
decision = interrupt({"draft": state["draft"], "question": "..."})
```

שימי לב: `decision` מתמלא רק כשממשיכים את הגרף. עד אז הקוד פשוט לא ממשיך מהשורה הזו.

### 3. `Command(resume=...)`

כך ממשיכים. מריצים את הגרף שוב עם אותו `thread_id`, ומעבירים את ההחלטה של האדם:

```python
graph.invoke(Command(resume={"action": "approve"}), config)
```

הערך שב-`resume` הוא מה ש-`interrupt()` מחזיר בתוך ה-node.

אותו `Command` משמש גם בכיוון השני: node יכול להחזיר `Command(update=..., goto=...)` כדי לעדכן את ה-state ולבחור לאיזה node ממשיכים. ככה `human_review` מחליט לאן הולכים, בלי conditional edge נפרד.

### 4. Checkpointer ו-`thread_id`

כדי לעצור ולהמשיך אחר כך, צריך איפה לשמור את המצב. זה תפקיד ה-checkpointer. כאן משתמשים ב-`InMemorySaver`, ששומר בזיכרון של התהליך.

ה-`thread_id` מזהה את השיחה. שני לקוחות שונים = שני `thread_id` שונים, ולכל אחד state משלו.

**בלי checkpointer, `interrupt()` לא עובד.**

בפרודקשן מחליפים את `InMemorySaver` ב-checkpointer שנשמר במסד נתונים (למשל Postgres), כדי שאדם יוכל לאשר גם אחרי שעה, אחרי restart של השרת, או ממסך אחר לגמרי. נדבר על זה בשיעור נפרד.

## המלכודת שכדאי להכיר

כשממשיכים אחרי `interrupt`, LangGraph **לא** ממשיכה מהשורה שעצרה. היא מריצה את כל ה-node מההתחלה, ורק הפעם `interrupt()` מחזיר מיד את הערך מ-`resume`.

המשמעות: כל מה שכתוב **לפני** `interrupt()` באותו node ירוץ פעמיים. אם שם נמצאת שליחת מייל או כתיבה ל-DB, היא תקרה פעמיים. לכן ה-node של העצירה נשאר נקי, והפעולה עצמה יושבת ב-node נפרד (`send_email`).

## איפה LangChain ואיפה LangGraph

מה שחשוב להבין שאלה שתי שכבות שונות:

**LangChain** אחראית על קריאה אחת למודל: הפרומפט, המודל, וה-parser, מחוברים ב-LCEL:

```python
draft_chain = DRAFT_PROMPT | llm | StrOutputParser()
```

**LangGraph** אחראית על הזרימה: איזה שלב רץ אחרי איזה, מתי עוצרים, ומה זוכרים בין השלבים.

### מה רואים בממשק

המסך מחולק לשניים. בצד אחד האינטראקציה: הודעת הלקוח, הטיוטה, וארבעה כפתורים להחלטה. בצד השני מה שקורה מאחורי הקלעים:

- **תרשים הגרף**, כשהצומת שהגרף עומד בו עכשיו מודגש בצהוב. כשהגרף עצר, רואים אותו תקוע על `human_review`.
- **לוג של מה רץ**: כל node שסיים, כל `interrupt`, וכל `resume` עם הערך שנשלח.
- **ה-state המלא** אחרי כל צעד.
- **מספר ה-checkpoints** שה-checkpointer שמר עד עכשיו.

הממשק לא מכיל לוגיקה של הגרף. הוא מייבא את `build_graph` מ-`main.py`, מריץ אותו עם `graph.stream(...)` ומציג את התוצאה. ככה רואים שה-UI הוא רק עוד דרך לשלוח `Command(resume=...)`, בדיוק כמו `input()` בטרמינל.

### הצעה למהלך ההדגמה

1. מפעילים את הגרף ומראים שהוא עצר על `human_review`, ושהטיוטה כבר נמצאת ב-state.
2. לוחצים "תיקון ע"י המודל" עם הערה, ומראים בלוג שהגרף חזר ל-`write_draft` ועצר שוב. זו הלולאה.
3. מאשרים, ומראים שרק עכשיו `send_email` רץ.
4. מתחילים מחדש ולוחצים "ביטול": `send_email` לא רץ בכלל.
5. מראים בלוג שאחרי כל `resume` גם `human_review` רץ שוב. זו המלכודת מהסעיף למעלה.

שם המודל מוגדר בראש `main.py` (`MODEL_NAME`). מה שנכון היום יכול להיות לא נכון מחר, כדאי להמשיך להתעדכן בדף המודלים של OpenAI.
